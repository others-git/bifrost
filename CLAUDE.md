# Bifrost — project directives for Claude

## High-level overview

Bifrost is a **smart-home control hub**.

- **Rooms are the core abstraction.** Provider-native groupings (Hue rooms/zones, Sonos rooms, …) are mirrored as `provider_groups` and wrapped by **Bifrost Rooms** (linked via `room_links`); the **"Sync"** button on a provider does this for both light and audio domains. A Room aggregates **any number of member devices** (lights and audio) and is the high-level control surface — power (all members), brightness (member lights), and volume/mute fanned out to the room's audio members, each with a **per-room volume offset** for loudness calibration (`room_audio_devices`, `PUT /rooms/{id}/audio/state`). Room controls are not a fixed list; they grow with the device mix, so keep this section current as capabilities land. A room also carries **configurable quick-control buttons** (`room_controls`, migration 0034, `PUT /rooms/{id}/controls` → `set_room_controls`): per-room glyph buttons rendered on the Control card **left of the room's power button** (which is itself a power-glyph button, not a switch), each doing one action — `power` (toggle chosen members), `volume`/`brightness` (open the shared `AudioEditor`/`LightEditor` scoped to chosen members), or `scene` (apply a scene). On the Control page a **long-press** on any device glyph is a quick power toggle (tap still opens the fly-out). **Per-room *configuration*** (lights/links membership, audio devices + offsets, quick-control buttons, enable/disable, merge) lives on the dedicated **Rooms page** (`frontend/src/pages/Rooms.tsx`); live control (on/off, color, scenes, quick volume) stays on the Dashboard / Floor Plan.
- **Scenes** are **server-side full-state snapshots** (snapshot + apply happen on the server; the frontend only sends ids), one unified model (`api::scenes`, `scenes`/`scene_entries` + `scene_power_entries`, migrations 0035 + 0038) **scoped by `room_id`**: a null `room_id` is a **Home Scene** (whole-home — every light + power device), a set `room_id` is a **Room Scene** (that room's effective members only). Both store each light's *full* `LightState` verbatim, so a running **dynamic effect is captured and reapplied** like any other attribute. (Effect is a **third mutually-exclusive light mode** alongside color and color-temp: `persist_light_state`/`LightStatePatch::apply_to` clear the other two when one is set — and normalize clear tokens `no_effect`/`off`/`none` to `None` via `models::is_clear_effect` — so `last_state` always names one honest mode and a snapshot never re-triggers a stale effect.) Capture (`capture_scene(name, room_id: Option)`) and apply (`apply_scene_entries`) are the **shared DRY engine** behind session/`v1`/MCP. A Home Scene can be the `is_default` "Restore Home" preset (`POST /api/scenes/restore-default`), surfaced as the gilded **Restore Home** seal on the Control page; handy after a power outage resets bulbs/switches. The old lossy **palette-scene** system (colors-only room *looks*) was **removed** (migration 0038 drops `palette_scenes`). Audio is intentionally **not** captured yet (the audio-aware capture goal — *selected* source/station, not the transient track — was deferred). All managed on the **Scenes page** (Home scenes + per-room Room scenes), and a room's scenes are saved/applied from its control fly-out (`SceneModal`).
- **Per-device control:** every device is also controllable independently of any Room (`PUT /api/lights/{id}`, `PUT /api/audio/devices/{id}/state`).
- **Floor planner** — a rough 2D plan of the home: paint tiles/walls, place devices roughly where they physically reside, and bind painted regions to Bifrost Rooms. Devices and rooms are controlled directly from the plan via **fly-outs** (popovers). It is purely an *alternate visualization* of the same devices — its controls reuse the same central control components and API actions as the Dashboard/Rooms (`LightEditor`, scene controls, `setLightState`/`setRoomState`/`setAudioState`), never a forked control path.
- **Everything is exposed via the API**, kept in sync with docs: `docs/api.md` (public `/api/v1`, Bearer-key) and `docs/mcp.md` (the embedded MCP server's tool catalogue). The MCP server is a **first-class Bifrost surface** (`src/api/mcp.rs`, served at `/mcp`), not a separate repo.

### Current providers

Registered in `ProviderRegistry::default_registry()` (`src/providers/mod.rs`). **Keep this list current when adding a provider.**

| Domain | Type key | Name | Transport |
|---|---|---|---|
| Light | `hue` | Philips Hue | SSE push |
| Light | `govee` | Govee | poll — **dual transport, LAN-preferred**: one provider owns both a cloud client (`openapi.api.govee.com`, API key) and a LAN client (local UDP); per device it prefers LAN when that device answered a scan (`mac_hw_id`-keyed MAC→IP cache) and falls back to cloud otherwise — for an unscanned device, a failed LAN send, or an effect/dynamic-scene (cloud-only). **LAN is on by default** (`bind_addr` defaults to `0.0.0.0` in the factory; cloud is the optional API-key part) — a host that can't reach the LAN just scans empty and uses cloud. Only **some** Govee devices support LAN (scan membership is the per-device gate). **Gotcha: the LAN scan is multicast — the socket must `join_multicast_v4`** (devices reply to `239.255.255.250:4002`); WSL2 can't bridge LAN bcast/mcast so LAN only works on real-L2 hosts (see memory `wsl2-no-lan-broadcast-multicast`). |
| Light | `lifx` | LIFX | poll — **dual transport, LAN-preferred** (same unified pattern as Govee): one provider owns a cloud client (`api.lifx.com` Bearer token) and a LAN client (`src/providers/lifx/lan.rs` — binary UDP/56700: `GetService`/`Get`/`SetColor`/`SetPower`, HSBK ⇄ xy/mirek). Per bulb prefers LAN when it answered a broadcast scan (process-wide MAC→addr cache; MAC is the unified id since the cloud id *is* the MAC) and falls back to cloud otherwise — for an unscanned bulb, a failed LAN send, or an **effect** (LAN effects not implemented). Groups stay cloud-only (`discover_groups`/`group_id:` one-call control). **LAN is on by default** (`bind_addr` defaults to `0.0.0.0`; cloud is the optional token part). LIFX LAN is on by default on the bulbs, so most are LAN-reachable. (LIFX uses broadcast + unicast replies, so unlike Govee it needs no multicast group join — but WSL2 still can't bridge broadcast, so LAN only works on real-L2 hosts.) |
| Integration | `ha` | Home Assistant | **WebSocket push** (`subscribe_events`/`state_changed` via `HaPushManager`, `ConnectionMode::HaPush`) — one connection keeps lights+audio+power live; REST for discovery/control |
| Audio | `onkyo` | Onkyo / Integra | eISCP — **one shared connection** per receiver (`OnkyoLink`): push + reads + writes multiplexed (incl. zone 2) |
| Audio | `sonos` | Sonos | UPnP; **GENA push + heartbeat poll** for live state, live grouping, favorites — **registered & addable; newest provider, least hardware-tested** |

**Audio groups vs zones.** A provider-native **sync group** (Sonos players playing in sync) is *not* a stored device — it's **derived from its members**: each member's `AudioState.group_coordinator` names the coordinator, and the UI collapses a room's members that share one into a single grouped control (`speaker_group` glyph). Don't reintroduce a "group device". A **fixed output zone** (Onkyo/AVR zone 2 — a second independent output of one box) *is* a normal audio device, assignable to its own room; it's not a sync group despite the `Zone` kind label.

**Receiver binding (M22).** A **source** audio device (TV / streamer / console) can be **bound to a receiver** that owns its volume (`audio_devices.receiver_id` + `receiver_source`, stored on the source, **many sources → one receiver**; migration 0026). The split lives in `AudioCommand::split_for_receiver` and is applied by `apply_audio_command` (the shared service fn, so session/`v1`/MCP all route identically): a bound source's `volume`/`mute` route to the receiver while `power`/`source`/`transport` stay on the source, and powering the source **on** wakes the receiver and switches it to `receiver_source` (power-**off** is not propagated — the receiver may serve other sources). Bind via `PUT /api/{,v1/}audio/devices/{id}/receiver` (`set_audio_receiver`; rejects self/unknown/chained), config on the Devices page. A bound source's read overlays the receiver's volume/mute.

**Unregistered (code kept, dropped from the add-provider menu):** `govee-lan`, `shelly`, `tasmota`, `wled`. Their `LightProvider`/factory code still lives in the tree; they're simply not `register`ed in `default_registry`, so the first-class set stays Hue, Govee, LIFX, Home Assistant, Onkyo, Sonos. Re-add a `register(...)` line to bring one back. `wled` is still the generic mockable light provider in the integration-test fixtures (`tests/helpers.rs::test_registry`). **`govee-lan` is special**: its `GoveeLanProvider` LAN transport is **not dead code** — it's owned internally by the unified `govee` provider (LAN-preferred control); only the standalone `GoveeLanProviderFactory` registry entry is dropped (LAN is configured via `govee`'s optional `bind_addr` field, not a separate provider row).

The **Domain** column above is the **add-provider UI category** (`ProviderDomain`: `Light` / `Audio` / `Integration`), set per-factory via `ProviderFactory::domain()` (defaults to `Light`). It is *not* the functional device domain.

**Home Assistant is a "high-class" provider** (`src/providers/ha`): one adapter surfaces *any* HA integration as Bifrost devices and imports **HA Areas as Bifrost Rooms** via the shared Sync flow. It's grouped under **"Integrations"** in the add-provider menu (`domain()` → `ProviderDomain::Integration`) because it isn't a single-device-domain provider. It's registered across **four device domains from one provider row** — `register(HaLightFactory)` (lights), `register_power(HaPowerFactory)` (switches/plugs/fans), `register_audio(HaAudioFactory)` (`media_player` — TVs/speakers), and `register_remote(HaRemoteFactory)` (`remote.*` — Android TV / streamers) — and the discover, sync, and `all_types` paths are all multi-domain-aware (one menu entry; devices fan out to the right tables). HA state is kept live by the **`HaPushManager`** — one persistent `subscribe_events`/`state_changed` WebSocket (`ConnectionMode::HaPush`, built like Hue's SSE) that fans each change onto the light/audio/**power** event pipelines (so `power_devices` now push live, not just poll). **Launching named content** ("play Bob's Burgers on the bedroom TV") is handled by the voice pipeline's **native-first, HA-Assist-fallback** rule: the deterministic grammar (`api::voice`) parses what it can, and any clause it can't is delegated to **HA Assist** (`HaProvider::converse` → `POST /api/conversation/process`), which resolves and acts on it. Onkyo is **active** (single-connection `OnkyoLink`); Sonos is **registered and addable** — push, favorites, and sync grouping are all implemented; it's just the newest provider and the least hardware-tested. (The `HaAudioFactory` doc comment still says "on hold" — stale; the registry actually `register_audio`s it.)

**Device domains.** Bifrost has four device-domain models, kept deliberately separate so each domain's state shape stays honest: **lights** (`models`), **audio** (`models::audio`), **power** (`models::power`) — the DRY home for *strictly on/off* devices (switches, plugs, fans, boolean helpers) — and **remotes** (`models::remote`, M25: a virtual remote — keys / text / app-launch — for TVs and streamers). A power device's only state is `on`; its `PowerKind` drives the UI glyph but not behaviour, so a switch isn't modelled as "a light with an empty capability set". Devices with genuinely richer state (climate, covers, …) get their own domain rather than being forced into one of these. HA's `PowerProvider` impl maps `switch.*`/`fan.*`/`input_boolean.*`. The power domain is **wired through the backend**: `power_devices` table (migration 0019, no `capabilities` column), `api::power` service layer shared by session (`/api/power/*`), `/api/v1/power/*`, and MCP (`list_power_devices`/`set_power`). One provider type can now serve **multiple device domains** from a single row — `register_power` alongside `register`, and `/api/providers/{id}/discover` is **additive** (discovers lights ∪ power ∪ audio for whatever the type is registered for). Power devices are Room members and a **pure** room on/off **fans out** to them (and to audio members) via `apply_room_state` — but a brightness/color/temp change does *not* (an attribute change with implicit `on:true` must not power on the room's speakers/switches; only an on/off with no light attributes fans to audio+power). Power state is now **pushed live** for HA via the `HaPushManager` WebSocket (`PowerEvent` → `power_db_writer_task` → `power_devices.last_state`; SSE `power_state` event consumed on the Dashboard); other providers still refresh on poll + live GET.

**Devices page & glyphs.** The **Devices page** (`frontend/src/pages/Devices.tsx`) is the full device *inventory* — every device of every domain (lights, audio, power), regardless of room membership. It's the **configuration** surface (enable/disable a device; pin a **glyph override**; assign a device to a **room** from the device side — `PUT /api/{lights,audio/devices,power/devices}/{id}/room` → `rooms::set_device_room`, one *direct* room per device, the counterpart to the room-centric membership setters; room *links* from synced provider groups are still managed on the Rooms page), not a control surface. Each device renders a glyph derived from its type/kind by default; a user can override it by name (`lights.glyph` / `audio_devices.glyph` / `power_devices.glyph`, migration 0024; `PUT /api/{lights,audio/devices,power/devices}/{id}/glyph` via the shared `set_device_glyph` helper). Glyphs are a single by-name registry (`frontend/src/components/glyphs.tsx`, `Glyph`/`GLYPH_OPTIONS`); the Control page and fly-outs render the **effective** glyph (`device.glyph ?? type default`).

**Cross-provider de-dup (`api::dedup`).** A physical device reachable both natively (Hue/Govee/Sonos/Onkyo) and via an integration (Home Assistant) imports as two rows. Providers stamp each device with a normalized hardware id where the hardware exposes one (`*.hw_id` = a `mac:<hex>` key via `providers::mac_hw_id`): HA from the **device registry** over WebSocket, Govee from the device MAC, Hue from the Zigbee `mac_address`, Sonos from the `RINCON_<mac>` uuid, Onkyo from the `NRI` device-info reply. After every discovery (and provider delete), `reconcile_duplicates` clusters by `hw_id` and **shadows** the integration copy under the native one (`shadowed_by`, `shadow_auto`; migration 0025): **native always wins** — the rule is `registry.ui_domain(type) == Integration` loses to single-domain native providers. A shadowed device stays tracked but is hidden from control and room membership (queries add `shadowed_by IS NULL`) and the Devices page collapses it. Matching is exact-MAC only (safe to auto-apply); the manual link `PUT /api/{…}/{id}/shadow` (`set_device_shadow`, `shadow_auto = 0`, never clobbered by the reconciler) is the no-hw_id fallback. **Capability parity, not dependence:** when HA surfaces a capability a first-class provider lacks, build it into that native provider rather than deferring to the HA copy. **Whenever you flag such a missing capability, file it in PLAN.md's _Capability-parity gaps (tracked)_ list in the same change** — de-dup hides the HA copy that had it, so an unfiled gap is a silently-lost capability.

## Test coverage is mandatory

Every public function, method, and non-trivial private helper must have test coverage.
There are no exceptions. This is not negotiable.

### Where tests live

| What | Where |
|---|---|
| Pure logic (crypto, models, color math, backoff) | `#[cfg(test)]` module at the bottom of the same file |
| Provider HTTP behaviour (Hue, Govee, future integrations) | `#[cfg(test)]` module in the provider file, using `wiremock` |
| API layer (Axum routes, auth, DB) | `tests/api.rs` using an in-memory SQLite app fixture |
| Cross-cutting integration | `tests/` as named files |

### Rules

- **New provider?** The `LightProvider` impl AND the `ProviderFactory::build` path must both be covered by wiremock tests before the code is considered done.
- **New API route?** At minimum: happy path + unauthenticated request returns 401.
- **New crypto helper?** Roundtrip test + at least one failure-mode test (wrong key, tampered data).
- **The full CI gate must pass locally** before any change is considered complete — CI runs all three and fails on any:
  ```
  cargo fmt --check
  cargo clippy --all-targets -- -D warnings
  cargo test
  ```
  Running only `cargo test` is not enough; fmt and clippy (with `-D warnings`) are equally blocking.
- Do not silence warnings with `#[allow(dead_code)]` to make tests pass. Fix the code.
- Keep the PLAN.md file in sync with "Active Milestone" as the header. Beneath that show what milestones we've completed as a simple one-liner. Open milestones for any new proposals or future work. 

### Test style

- Prefer real behaviour over mocks. Use `wiremock` for external HTTP; use real in-memory SQLite for DB tests.
- Test public contracts, not implementation details. Avoid testing private internals directly.
- Each test has one clear assertion purpose. Name it after the behaviour: `discover_returns_empty_list_when_bridge_has_no_lights`, not `test1`.
- Inline test helpers are fine; large shared fixtures go in `tests/helpers.rs`.

## Other directives

- The `ProviderRegistry` is the single place where provider types are registered. Do not add provider-type match arms anywhere else.
- Credentials are encrypted with AES-256-GCM before persisting. Never store plaintext credentials in the DB.
- The Hue connection manager must be the only code that reconnects to the bridge SSE stream. Do not open a second stream anywhere.
- The Floor Planner is a visualization layer only. Device and room controls there must be fly-outs that reuse the shared control components and API actions the Dashboard/Rooms use — never reimplement control UI or logic per view.
- The session API (`/api/*`), the public API (`/api/v1/*`), and the embedded MCP server (`/mcp`, `api::mcp`) all delegate to the **same shared service functions** (in `api::lights` / `api::audio` / `api::rooms` / `api::palette_scenes`). Put control/behaviour in the service layer, not duplicated per router, so the three surfaces can't drift. MCP tools are a third caller of those fns — never a forked control path, and never an HTTP hop back into `/api/v1`.
- Migrations are **append-only**: add the next `migrations/NNNN_*.sql`; never edit a migration that has shipped.
- **Cutting a release? Use `scripts/release.sh <X.Y.Z> "<summary>"`** — the one-shot release wrapper (lives in both this repo and the kiosk repo). It runs the **CI gate first** (Bifrost: `cargo clean -p bifrost` then `fmt --check` · `clippy -D warnings` · `test`; kiosk: `./gradlew testDebugUnitTest`) and aborts with a clean tree if it fails, then **bumps the version in lockstep with the tag**, stages everything, commits `Release X.Y.Z — <summary>` (with the Co-Authored-By trailer), annotated-tags `vX.Y.Z`, and pushes the branch + tag. It auto-detects the repo and bumps the right file: **Bifrost → `Cargo.toml` + `Cargo.lock`**, **kiosk → `app/build.gradle.kts` (`versionName` + `versionCode` +1)**. Emergency gate bypass: `SKIP_GATE=1 scripts/release.sh …`. Run it instead of doing the gate/bump/commit/tag/push by hand — that's the whole point.
  - **Why the version bump matters (what the script enforces):** `Cargo.toml`'s version is the *single source* of the in-app version: `env!("CARGO_PKG_VERSION")` → the `/api` health endpoint (`src/api/mod.rs`) → the frontend version badge (`App.tsx`). Forget it and the binary **and** the badge silently lag the release (e.g. 0.14.0 shipped reporting `v0.13.0` because `Cargo.toml` stayed at 0.13.0). The tag tracks shipped versions, so the in-file version must always match it — which is exactly what `release.sh` guarantees.
- Frontend has no CSS framework — inline style objects plus `frontend/src/styles.ts` (`S`, `ACCENT`). Reuse the shared control components (`LightEditor`, `components/scenes`, `components/dialogs`) rather than re-implementing controls.
- **Responsive:** inline styles can't express media queries, so branch layout on the **`useViewport()`** hook (`frontend/src/useViewport.ts`) — **`isCompact` (≤1024px = phones *and* tablets) is the primary layout switch**. Both get the **mobile chrome** (top title bar + bottom tab bar in `App.tsx`, touch sheets, stacked/dense cards), because a wall-mounted **tablet is a first-class target**: the goal is to run Bifrost on a dedicated tablet as a static, always-on home-control fixture, so a tablet must *look and feel like mobile*, never like a shrunk desktop. Anchored fly-outs (`LightEditor`/`AudioEditor`/`PowerFlyout`) become bottom sheets via `components/sheet.ts`. `isMobile` (≤640px, phones only) is reserved for the few things a phone genuinely can't fit — today only the **Floor Plan** (hidden on phones, shown on tablet fixtures); don't use it as the general layout switch.
- **Compact-friendly is mandatory for every new UI element, not an afterthought.** Any new control (picker, popover, menu, dialog, inline editor) must have a touch-friendly form for compact viewports: branch on `useViewport().isCompact` and render a **bottom sheet** (full-width, large ≥44px tap targets, scrollable) instead of a tiny anchored desktop popover; avoid native `<select>`/hover-only affordances in dense card rows (they crowd the layout and truncate content). Build the compact path in the same change as the desktop one. Phones and tablets share this path.
- **Reliability is a primary goal** (it's why Bifrost exists vs Home Assistant). Connection managers own reconnection with shared backoff; a live read that can't reach a device falls back to cached state with `reachable: false` rather than failing the whole request.
- **Keep docs in sync as part of the change:** new `/api/v1` route → `docs/api.md`; new assistant-facing capability → `docs/mcp.md`; new provider → the Current providers table above.

## Adding a provider

1. Implement the factory + `LightProvider`/`AudioProvider` (and `discover_groups` if the provider has native rooms/zones to wrap into Bifrost Rooms).
2. Register it in `ProviderRegistry::default_registry()` (`src/providers/mod.rs`) — the only place provider types are registered.
3. Add a row to the **Current providers** table above.
4. wiremock tests for the provider impl **and** the factory `build` path (mandatory — see Test coverage).
5. Declare `credentials_schema` so the add-provider form renders the right fields.
