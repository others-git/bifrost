# Bifrost — project directives for Claude

## High-level overview

Bifrost is a **smart-home control hub**: Rust/Axum backend + embedded web UI in one static musl binary, SQLite (WAL). Credentials are AES-256-GCM encrypted at rest; API keys (`bfr_…`) are SHA-256-hashed. Competitive target: Home Assistant — specifically fixing its Hue-bridge reliability. The session API (`/api/*`), public API (`/api/v1/*`, Bearer), and embedded MCP server (`/mcp`, `src/api/mcp.rs`) all delegate to the **same shared service layer** — never forked per surface — and are kept in sync with `docs/api.md` (v1) and `docs/mcp.md` (tool catalogue).

- **Rooms are the core abstraction.** Provider-native groupings (Hue rooms/zones, Sonos rooms) are mirrored as `provider_groups` and wrapped by **Bifrost Rooms** (linked via `room_links`); a provider's **"Sync"** button does this for lights and audio. A Room aggregates any number of member devices and is the high-level surface: power (all members), brightness (member lights), and volume/mute fanned to audio members each with a **per-room volume offset** (`room_media_devices`, `PUT /rooms/{id}/media/state`). It also carries **configurable quick-control buttons** (`room_controls`, mig 0034, `PUT /rooms/{id}/controls` → `set_room_controls`): per-room glyph buttons left of the room's power-glyph button, each one action — `power` (toggle chosen members), `volume`/`brightness` (open the shared `MediaEditor`/`LightEditor` scoped to chosen members), or `scene`. On the Control page a **long-press** on a device glyph is a quick power toggle (tap opens the fly-out). Per-room **configuration** (membership incl. sensors, audio devices+offsets, presence opt-outs, quick buttons, enable/merge/delete) lives on the **Rooms page** (`pages/Rooms.tsx`): each room is a "charter" card — engraved name, link chips, a **domain census strip** (one `nicheStyle` glyph niche per domain in its accent, each opening the editor at its section) and a live **occupancy rune** — expanding into ONE stacked editor (Members → Audio → Presence → Quick controls, destructive ops quiet at the bottom). The Audio section never assumes one speaker per room: every member row shows its own live level (shared `setMediaState` plane) + offset trim, with the room-sweep fan-out slider as a test action. Live control stays on Dashboard / Floor Plan.
- **Scenes** are **server-side full-state snapshots** (frontend sends ids only): `api::scenes`, `scenes`/`scene_entries`+`scene_power_entries` (mig 0035/0038), **scoped by `room_id`** — null = **Home Scene** (every light + power device), set = **Room Scene** (that room's effective members). Each light's *full* `LightState` is stored verbatim, so a running **dynamic effect is captured and reapplied** like any attribute. Effect is a **third mutually-exclusive light mode** vs color and color-temp: `persist_light_state`/`LightStatePatch::apply_to` clear the other two when one is set, and normalize clear tokens (`no_effect`/`off`/`none`) to `None` via `models::is_clear_effect`. `capture_scene`/`apply_scene_entries` are the shared engine behind session/`v1`/MCP. A Home Scene can be the `is_default` "Restore Home" preset (`POST /api/scenes/restore-default`), the gilded seal on the Control page. Audio is not captured yet. Managed on the **Scenes page** + a room's control fly-out (`SceneModal`).
- **Per-device control:** every device is controllable independently of any Room (`PUT /api/lights/{id}`, `PUT /api/media/devices/{id}/state`).
- **Floor planner** (`pages/FloorPlan.tsx`) — a rough 2D plan: paint tiles/walls, place devices, bind regions to Rooms. An *alternate visualization only*; its fly-outs reuse the shared control components/actions (never a forked path). **Tabled: its nav entry is dev-mode only** (`App.tsx` gates it on `settings.dev_mode`, updated live by the Settings → Developer toggle); the page itself still works when reached.
- **Boards** — user-composable dashboards (`api::dashboards`, `dashboards` table, mig 0045; `pages/Boards.tsx`). A board has a **fixed aspect ratio** chosen at creation (`dashboards.aspect`, mig 0046; e.g. `16:9` or a tablet's `18.5:9`, decimals allowed; `models::dashboard::clean_aspect` validates) and is a **drag-resize grid** whose canvas is **letterboxed to that aspect** — sized only from the container + aspect, never widget content (content-driven height caused a measure→grow→re-measure runaway). The grid is `GRID_BASE`(48) cells on the long axis, short axis scaled for ≈square cells (`aspectGrid`); a widget is a fraction of the canvas, so a board looks identical (scaled) on any screen. Edit mode shows tiered guides (center cross / quarter lines / fine cells). **Widget content scales with the canvas** so a board reads the same (just scaled) on any screen — the two mechanisms: **readout widgets** (clock/sensor/weather/now-playing) + the **label** self-scale their type via a CSS size-container (`cqmin`), while the **fixed-px shared-Control widgets** (room/device/group/button/control) get a canvas-relative CSS **`zoom`** on their content wrapper (`contentZoom = canvasW / REFERENCE_CANVAS_W`, clamped) — `zoom` scales the whole fixed-px subtree (glyphs, `TILE_LABEL`, `GlyphButton` sizes, slider text) *and* participates in layout, so the shared components stay untouched (no Control-page risk) and hit-testing still works. The two sets are mutually exclusive (`SELF_SCALING_WIDGETS`) to avoid double-scaling. **Room widgets go one further** (`FIT_ZOOM_WIDGETS`): instead of the global canvas zoom, `WidgetBox` binary-searches the largest zoom whose content doesn't overflow (the `RoomCard` widget body self-tags `data-bf-scrollport` as the measure point; a childList MutationObserver re-fits when membership lands/changes) — so the glyph-button rows grow to fill the tile with no dead space, and an overflowing in-between state just falls back to the body's scroll. A widget authored on a desktop therefore renders correctly on an 8.7" wall tablet — the class of bug the preview mode surfaces. Widgets persist as one JSON `layout` blob; the backend is a **generic layout store** that never interprets `type`/`config`, so new widget types need **no backend change**. A board can carry a **background** (`dashboards.background` JSON — opaque to the backend like widget config, mig 0060; edited in the Edit-board modal): an **upload** (image/gif/short mp4-webm loop, ≤25MB, `PUT/GET/DELETE /api/dashboards/{id}/background/media`, mime-allowlisted, cache-busted via a `v` stamp) or a **preset** rendered by `components/BoardBackground.tsx` — synthwave horizon (noise-terrain neon grid), circuit filigree (engraved traces + travelling pulses), astrolabe night, ember drift, aurora veil (CSS keyframes), day/night sky (real-clock palette), weather-lit (condition read from the board's own weather widget) — plus a legibility **scrim** (dim slider), speed, and a still-frame toggle. Kiosk-friendly by construction: one canvas at ~30fps, rAF (screen-off costs zero), visibility pause, `prefers-reduced-motion` honoured, no CSS filter blurs; presets sample the live `--bf-*` theme tokens. **Hidden in edit mode** so the grid guides stay legible. The same spec carries the board's **"Match theme" appearance override** (`match_theme`): widget accents wear the theme's domain colours instead of actual light chromas/effect gradients — via `MatchThemeContext` (`components/appearance.tsx`), consulted inside the shared components (`RoomCard` light buttons/plate hexes, the Boards tiles), defaulting false everywhere else so Control/Rooms/Floor Plan are untouched. Widget types (**room** — the shared `RoomCard` on a board plate, device tile, **button**, **device group**, now-playing, scene/Restore-Home, custom control, **sensor** — a generic-device readout in a configurable display style: number / gauge arc / vial / bar / state-glyph, with optional min/max range, decimals, and warn/alert/flash thresholds whose direction is configurable (`bad_direction`) and whose accent escalates gold → bright gold → rose with plate bloom — `flash_at`, the top tier, keeps alert's rose but blinks the accent-lit part (fill/arc/glyph + plate chrome, `bifrost-sensor-flash`, reduced-motion holds steady), **device status** — one plate for a generic device showing a user-chosen set of its readouts (`keys`) as label·bar·value rows (the litter box as one tile), **feed** — "Recently added" over a configured feed source (see the `plex` provider row): source + library + tile count + layout config (`layout`: poster shelf default, `column` = thumb+text rows for tall placements) + optional `overflow` (extra items loaded past the visible `limit`, revealed by drag-scroll — mouse drag with click-suppression so browsing never fires the tap action, native pan on touch, scrollbar hidden), 60s poll (feeds have no SSE), posters via the hub's token-holding proxy, and an optional per-widget tap action `{remote_id, app, activity}` that launches the item's deep link (or the configured app as fallback) on a TV through the shared remote command plane, weather, clock, label) all **reuse the shared control components** (`DeviceControl`, `RoomCard`, `GlyphButton`/`RoomControlButton`, `LightEditor`/`MediaEditor`, `CornerFiligree`, `nicheStyle`/`InlineSlider`) — never a forked path — and stay live off the `/api/events` **SSE** stream (sensors poll). **Board edits are live too:** every dashboards mutation (layout/name/aspect/background/create/delete/reorder) fires `notify_inventory("dashboards")`, and an open Boards view re-reads its boards on that payload — skipped while locally in edit mode so a remote change can't clobber an in-progress drag — which is what keeps a kiosk's board current without exiting and re-entering. A board can go full-screen **("kiosk")**, and a paired kiosk can **auto-launch a board** on load: assigned **per-kiosk from a main (non-kiosk) client** (Settings → Clients; `kiosks.default_board_id`, mig 0047, `PUT /api/kiosks/{id}/board`); the kiosk-served Boards page resolves *its own* assignment via `GET /api/kiosks/self` (auth'd by the WebView's `bfr_key` cookie). A **preview mode** (view-only, desktop) locks the canvas to a target device's exact CSS pixel size and scales-to-fit, so widget/font proportions read true when composing an 8.7" wall-tablet board on a big screen — fonts/glyphs are fixed px, so only the device's *viewport size* differs, and rendering at that size is what makes scale honest. The device menu offers stock presets **plus your live kiosks by their real reported viewport**: a kiosk's web client reports `window.innerWidth×innerHeight` on load (`PUT /api/kiosks/self/viewport`, `kiosks.viewport_w/h`, mig 0058) — measured, not guessed. Session-only UI config — **not** on `/api/v1` or MCP.

**Self-healing LAN hosts (`connection::relocate`, ~30s watch).** A power outage hands devices fresh DHCP leases, and any provider pinned to a stored IP silently drops off every surface until someone re-configures it. A provider type opts into healing by declaring a **`LanBinding`** (`providers::LanBinding`, returned from its factory beside `discoverer()` — the registry is still the one place types are declared): *which credential key holds the address* (`host` / `bridge_ip` / `device_ip`), *which TCP port proves it alive*, and *is this candidate the same device*. The loop probes each enabled binding's stored host; when one is dead it re-runs that **type's own discovery legs** (the same union the "Scan network" button runs, one scan per type per pass) and rebinds the credentials — host field only — ONLY to a candidate that proves identity, then restarts the manager so push channels and pollers reattach immediately. **Two proofs, in cost order:** a discovery candidate carrying one of the provider's known `hw_id`s (collected across *every* device table: mDNS `bt` MAC, Onkyo `ECN` MAC, Kasa `get_sysinfo`), or the binding's own live check — a Bravia's ScalarWeb MAC, a Sonos player's `UDN` (any household player counts; the row is an entry point, not a device), or, for token-bound gear whose API exposes no MAC (Hue's app key, Nanoleaf's auth token), a credential only the real device accepts. A candidate that names itself with a **different** `hw_id` is rejected outright — no live check can overturn a self-identification — so the expensive path runs only for anonymous candidates, under a hard `VERIFY_TIMEOUT` so one slow host can't stall the watch. **Anything short of proof answers `false`** — rebinding onto a neighbour's device is strictly worse than staying lost — and a candidate at an address **another provider row already owns** is skipped entirely (shared `known_provider_hosts`): it's a device Bifrost already manages, so adopting it would point two rows at one device rather than heal anything. Two guards keep the watch cheap: `LanBinding::can_verify` skips a provider *before* scanning when nothing could ever prove it (a TV known only by the `host:<ip>` id derived from the address that just changed — see `is_portable_hw_id`), and the stored-host probes run concurrently so an outage's wall time doesn't grow with the device count. A failed attempt **backs off** (doubling to ~16 min) so an unplugged device doesn't scan the network every tick. **Who participates:** every address-pinned LAN type (`hue`, `nanoleaf`, `kasa`, `onkyo`, `sonos`, `smarttv`). Cloud providers and the MAC-addressed LAN transports that re-resolve on every scan (Govee/LIFX LAN) have no stale address to heal, and HA is excluded deliberately — its host is a server URL the user typed, not a discovered device.

**Audio groups vs zones.** A provider-native **sync group** (Sonos players in sync) is *not* a stored device — it's **derived** from each member's `MediaState.group_coordinator`, and the UI collapses a room's members that share one into a single grouped control (`speaker_group` glyph). Don't reintroduce a "group device". A **fixed output zone** (Onkyo/AVR zone 2) *is* a normal audio device assignable to its own room — not a sync group, despite the `Zone` kind label.

**Receiver binding.** A **source** device (TV/streamer/console) can be **bound to a receiver** that owns its volume (`media_devices.receiver_id`+`receiver_source` on the source, **many sources → one receiver**, mig 0026). The split (`MediaCommand::split_for_receiver`, applied by the shared `apply_media_command`): `volume`/`mute` route to the receiver, `power`/`source`/`transport` stay on the source; the receiver **mirrors the source's power** (on wakes it and switches it to `receiver_source`; off takes it down too — the bound pair is one appliance, and commands are absolute so an already-matching receiver is a no-op). Bind via `PUT /api/{,v1/}media/devices/{id}/receiver` (`set_media_receiver`; rejects self/unknown/chained). A bound source's read overlays the receiver's volume/mute. **Composite power-on also wakes a paired remote:** for `power:true`, `apply_media_command` fans power-on to the media device's paired enabled remote (`remote_devices.paired_media_id`) via `apply_remote_command` (WoL nudge + provider `turn_on`) — the reliable wake when a standby TV's `media_player` is unavailable; success if **either** path works. (See `docs/composite-devices.md`.)

**Unregistered (code kept, off the add-provider menu):** `govee-lan`, `shelly`, `tasmota`, `wled` — `LightProvider`/factory code still in-tree, just not `register`ed; re-add a `register(...)` line to revive one. `wled` is the generic mockable light provider in test fixtures (`tests/helpers.rs::test_registry`). **`govee-lan` is special:** its `GoveeLanProvider` LAN transport is **not dead code** — it's owned internally by the unified `govee` provider; only the standalone factory registry entry is dropped.

**Home Assistant is a "high-class" provider** (`src/providers/ha`): one adapter surfaces *any* HA integration as Bifrost devices and imports **HA Areas as Bifrost Rooms** via Sync. Grouped under **"Integrations"** in the add-provider menu (`domain()` → `ProviderDomain::Integration` — the menu category, *not* the device domain). Registered across **five device domains from one row** — `register(HaLightFactory)`, `register_power(HaPowerFactory)` (switch/plug/fan), `register_media(HaMediaFactory)` (`media_player`), `register_sensor(HaSensorFactory)` (`binary_sensor`/`sensor`, allowlisted to motion/occupancy/contact/lux/temp/humidity), `register_remote(HaRemoteFactory)` (`remote.*`) — with discover/sync/`all_types` all multi-domain-aware. The **`HaPushManager`** WebSocket fans each change onto the light/audio/**power**/**sensor** event pipelines. **Launching named content** ("play Bob's Burgers on the bedroom TV") follows the voice pipeline's **native-first, HA-Assist-fallback** rule: the deterministic grammar (`api::voice`) parses what it can; anything it can't is delegated to **HA Assist** (`HaProvider::converse` → `POST /api/conversation/process`).

**Device domains.** Five typed domains plus a sixth **generic "passthrough"** escape hatch, kept separate so each state shape stays honest: **lights** (`models`), **media** (`models::media` — speakers, receivers, and TVs/streamers; mirrors HA's `media_player`; table `media_devices`, mig 0042; `/media` is the only path), **power** (`models::power` — strictly on/off: switches/plugs/fans/boolean helpers; only state is `on`, `PowerKind` drives the glyph not behaviour), **remotes** (`models::remote` — virtual keys/text/app-launch for TVs/streamers), **sensors** (`models::sensor` — **read-only** inputs: motion/occupancy/contact/illuminance/temperature/humidity; the leanest domain — no writes, just a `SensorReading` + reachability; table `sensor_devices`, mig 0051; `SensorKind::is_presence()` marks motion/occupancy). Devices with genuinely richer state (climate, covers) get their own domain rather than being forced into one of these. **Sensors aggregate into Rooms:** `rooms::room_occupancy` resolves a Room's occupancy (`Some(true/false)` from its enabled, non-shadowed presence members; `None` if it has none) — the provider-agnostic property presence-driven behaviour reads. **Which sensors count is configurable per room** (`room_presence_excluded`, mig 0057, `PUT /api/rooms/{id}/presence`): every presence member counts by default (a newly synced sensor participates automatically), opt-outs are filtered inside the one shared `room_presence_readings`, so kiosks/automations/gates all inherit the exclusion; an excluded sensor stays a member with visible readings. Configured in the room's Presence section (`components/RoomPresence.tsx`), which also shows the live verdict + a "Drives:" consumers line (kiosks + automations reading this room's occupancy). First consumer: the **kiosk display scheduler** (`api::kiosks::run_scheduler`) drives a wall tablet's screen from its **per-hour display plan** (`kiosks.hour_modes`, mig 0059, `PUT /api/kiosks/{id}/plan`): a paintable 24-char timeline — `W` awake (forced on) · `S` asleep (forced off, beats an occupied room) · `A` aware (follows the assigned room's occupancy with the no-motion grace) — painted in Settings → Clients (`KioskDisplayPlan`); `schedule_enabled` is the master switch, and a kiosk with **no painted plan** falls back to the legacy sleep-window + presence-flag pair (`combined_desired_awake`, mig 0052) so existing kiosks keep working untouched. The scheduler is **event-driven**: an occupancy verdict flip (or a display-policy config edit) pokes an immediate pass via `OccupancyWatch` (`rooms::OccupancySeen` — the shared verdict map + `Notify`), so presence wake is push-latency; the 30s tick is the fallback that catches hour boundaries and grace-timeout expiry. **Kiosk mic presence** (mig 0061, `PUT /api/kiosks/{id}/mic`): a kiosk's always-on microphone doubles as a room occupancy sensor — the app computes sound LEVEL on-device (`NoiseMonitor`/`NoiseDetector`: adaptive two-rate ambient baseline, two-window confirmation, 20s hangover; **audio never leaves the tablet**) and posts elevated/quiet edges to `POST /api/kiosks/self/noise` (bfr_key cookie), which injects a `SensorEvent` into the SHARED sensor pipeline via the internal `kiosk` pseudo-provider's manager-less push channel (`api::kiosks::ensure_kiosk_sensor_channel` → `ConnectionRegistry::ensure_sensor_push_channel`) — so the minted `sensor_devices` row (kind `occupancy`, follows the kiosk's room assignment) participates in room presence, automations, and SSE like any other sensor. Configured per kiosk in Settings → Clients (toggle + low/med/high sensitivity + live dB telemetry). **Aware override** (mig 0062, `PUT /api/kiosks/{id}/aware-override`): while any configured device (light/media/power, reusing the room-control `ControlTarget` shape) is on, an Aware hour overrides the display in a configurable direction (`AwareOverrideMode`): **keep_on** (default) reads the room as occupied regardless of actual presence — "don't let the screen sleep from a no-motion timeout while the TV is playing" — while **keep_off** forces the screen asleep, beating presence and governing even a sensorless room — "movie night: kill the tablet glow while the TV is on." Stored in the one `aware_override_targets` JSON column (`{mode, targets}`; legacy bare-array rows parse as keep_on). `scheduler_tick` checks it only during a `PlanMode::Aware` hour, reading each target's cached on-state via `automations::cached_device_on` (the same helper the automation engine's own device-stay-timer re-check uses); a keep_on hit also refreshes the presence grace timer, so the device turning back off hands smoothly to the normal no-motion countdown instead of going dark instantly. Configured per kiosk in Settings → Clients (`KioskAwareOverride`, shown only once the kiosk's plan has a painted Aware hour) via the same mixed-domain device picker as a room's quick-control targets. Reacts on the scheduler's existing 30s fallback tick (a config edit still pokes immediately) — no dedicated push subscription for target-device state changes, since the presence grace window already absorbs that latency. **Automations** (`api::automations`, `automations` mig 0054, session `/api/automations`): IFTTT-style rules whose **trigger is a tagged input** (`models::automation::AutomationTrigger` — `{kind:"sensor", sensor_id, event}`, `{kind:"room", room_id, event}` — a Room's aggregate occupancy (`rooms::room_occupancy`, recomputed per presence event with the engine's own reading overlay) makes the same boolean transitions — and `{kind:"device", domain: light|media|power, device_id, event}` — a device's power boolean ("the TV turns on"), fed by the same light/media/power push streams that keep the UI live; **on-demand media providers (Smart TV) get a demand-driven poller** (`connection::media_demand_poll_loop`) that stays idle until an enabled automation watches one of their devices, then polls at 5s with changed-only broadcasts, so a TV switched on with its own remote fires rules within seconds and an unwatched provider gets zero background traffic; and `{kind:"schedule", hour_modes}` — a **timer**: the kiosk plan's painted 24-char timeline (the shared `models::automation::PlanMode`/`plan_mode`/`plan_desired`/`is_valid_hour_plan` — kiosks import the same fns) restricted for automations to **W/S (On/Off) hours only** ('A' rejected — Aware is a kiosk display mode) and to **pure-power actions** (`is_power_only` — Room/Light `{on}` with no attribute clauses, Power; scenes/apps/toggles rejected, `restore_secs` rejected), driven as a state with edge detection (`evaluate_schedules` — hour-gated: the 5s tick early-returns until the local hour changes, rule edits force a pass via `automations_changed`, and a failed rules read leaves the verdict map untouched so a transient DB error can't re-fire active timers as first observations): the On edge fires gated by conditions only (cooldown is skipped by the engine AND rejected at write time — it could only swallow a later On window; the actions power the targets on with power-only writes, so a light comes back in its own colour) and the Off edge powers the SAME targets off (`execute_schedule_off`, unconditional — off is the safety direction); nothing re-applies while an hour holds, so a manual change sticks until the next boundary; a restart reconciles the On direction only (first observation while Off does nothing — never a mass power-off at boot; the next real Off edge squares it); UI: the editor opens with a **Trigger | Timer** category `Segmented` (future categories slot in) — Timer paints the shared **`components/HourPlan.tsx` `HourPlanEditor`** (extracted from `KioskDisplayPlan`, which renders the same control) with On/Off brushes, and its "Then" is a room-grouped `OptionCheckList` of rooms/lights/switches rebuilt into one power-on step on save; new input kinds need no schema change, `automations.sensor_id` is just a denormalized lookup column). Events are **edge-triggered** (`became_true`/`became_false`/`clear_for{secs}`/`held_for{secs}`/`rose_above`/`dropped_below` — the stay pair share one watched-state timer seam, `stay_watch`/`arms_stay_timer`); optional gates (time window with weekday filter, other sensors' readings, other rooms' occupancy — fail closed); actions replay through the **shared service layer** (`apply_room_state`/`apply_light_state`/`apply_power_state`/`apply_scene_entries` — never a parallel path). **Timed hold** (`restore_secs`, mig 0055): on fire the rule snapshots every touched device's pre-fire state (`RestoreEntry`; rooms/scenes expand to members) into `automation_restores`, re-applies it when `restore_at` passes (engine tick; persisted, so holds survive restarts); a re-fire extends the timer but keeps the original snapshot, and overlapping holds **inherit the first capture** per device (`pending_hold_entries`) so the final restore is the true pre-automation state regardless of timer order. **Manual override wins:** the engine watches every held device on the same push streams (`AppState.hold_watch`; per-device reference state seeded from the just-written cache, a grace window absorbs provider echoes — poll providers rebroadcast full state every cycle, so detection is toleranced changed-only, never event-presence) and a genuine external change releases that device from every pending snapshot instead of being clobbered at restore time. The engine (`run_engine`, spawned in `lib.rs`) rides the same sensor push streams as SSE, re-reads rules per event (edits are instant), re-arms stay timers across restarts, and exposes `POST /api/automations/{id}/run` (execute actions now, skipping trigger/conditions). UI: the **Automations page** (`pages/Automations.tsx`, nav above Settings) + a sensor's detail panel on Devices — both arrange the shared `components/Automations.tsx` primitives (`AutomationsModal`/`AutomationRow`/`useAutomationData`). Power is wired through the backend (`power_devices`, mig 0019; `api::power` shared by session/`v1`/MCP `list_power_devices`/`set_power`; pushed live via `HaPushManager` → SSE `power_state`). **One provider type can serve multiple domains** (`register_power` alongside `register`); `/api/providers/{id}/discover` is **additive** (lights ∪ power ∪ audio for whatever's registered). A **pure** room on/off fans out to power + audio members (`apply_room_state`); a brightness/color/temp change does **not** (an attribute change with implicit `on:true` must never power on the room's speakers/switches). The room-state body is **patch-shaped** (`apply_room_patch`): explicit `on` = power intent (whole room); no `on` = an attribute-only cascade onto **lit lights only** (never wakes an off lamp, skips native group calls, no media/power fan-out) — the UI's room sliders send this via `roomLightWrite`, while scenes/automations ("turn on and…") keep explicit `on`.

**Generic "passthrough" domain (`models::generic`).** The escape hatch for HA's controllable long tail Bifrost doesn't natively model — climate, cover, lock, `number`, `select`, `button`, scene, weather, vacuum, …. Discovery is a **denylist, not an allowlist** (`GENERIC_HA_EXCLUDED_DOMAINS`): *everything* is surfaced except domains Bifrost handles natively (light/switch/fan/media_player/remote — would duplicate + fight de-dup) and read-only/infra noise (`sensor`/`binary_sensor`, presence, HA plumbing). This keeps it a true escape hatch — a new HA device type appears with **no code change** (an unmapped domain still renders a state readout); add a `controls_from_ha`/`control_write_to_ha` arm only to give it richer controls. A generic device is a set of control **primitives** (`Control`: Toggle/Number/Enum/Button/Readout), so one mapping + one fuzzy UI covers dozens of HA domains: `controls_from_ha(domain, state, attrs)` derives them on read, `control_write_to_ha(domain, key, value)` maps a write to the HA service (`temperature`→`climate.set_temperature`, `position`→`cover.set_cover_position`, …). **Deliberately live, NOT persisted** — no table; `api::generic` (`/api/generic/devices`, `PUT …/control`) discovers across every provider registered via `register_generic` (HA today) per request. Frontend: the **"Other devices"** section on the Devices page (`components/GenericDevices.tsx`). **High-value domains (climate especially) should graduate to a real native domain over time** (same capability-parity rule). Dev-mode introspection drives the mapping: `GET /api/dev/devices/{provider_id}/{device_id}/raw` returns the raw upstream view — for HA the entity + a `generic_preview` of how it'd map; for Hue the CLIP v2 resource with that id plus its owner resource (`HueProvider::raw_resource`).

**Devices page & glyphs.** The **Devices page** (`pages/Devices.tsx`) is the full device **inventory** (every domain, regardless of room) and the **configuration** surface — enable/disable, pin a **glyph override**, and assign a device to **one direct room** from the device side (`PUT /api/{lights,audio/devices,power/devices}/{id}/room` → `rooms::set_device_room`; room *links* from synced groups stay on the Rooms page). Glyph override lives on `{lights,media_devices,power_devices}.glyph` (mig 0024, `PUT …/glyph` via `set_device_glyph`); the **effective** glyph rendered everywhere is `device.glyph ?? type default`. (Glyph registry + the "add a glyph" rule live under **Frontend & UI conventions**.)

**Cross-provider de-dup (`api::dedup`).** A device reachable both natively and via HA imports as two rows. Providers stamp a normalized `*.hw_id` (`mac:<hex>` via `providers::mac_hw_id`) where the hardware exposes one (HA device registry; Govee MAC; Hue Zigbee `mac_address`; Sonos `RINCON_<mac>`; Onkyo `NRI`). After each discovery/delete, `reconcile_duplicates` clusters by `hw_id` and **shadows** the integration copy under the native one (`shadowed_by`/`shadow_auto`, mig 0025): **native always wins** (`registry.ui_domain(type) == Integration` loses to single-domain native providers). A shadowed device stays tracked but is hidden from control/membership (queries add `shadowed_by IS NULL`). Matching is **exact-MAC only** (safe to auto-apply); the manual `PUT /api/{…}/{id}/shadow` (`set_device_shadow`, `shadow_auto=0`, never clobbered by the reconciler) is the no-`hw_id` fallback. **Capability parity, not dependence:** when HA exposes a capability a native provider lacks, build it into the native provider — and **flag the gap explicitly in the same change**, since de-dup hides the HA copy that had it (an unfiled gap is a silently-lost capability).

## One control plane per capability — shared end to end, never bespoke per page

**This is the hardest rule in the project. Per-page control logic is the single biggest source of recurring "works here, broken there" bugs — do not write it.** A "control plane" is the full path that moves one capability (a light's color, a speaker's source, a room's power): backend service fn → API → frontend component → device. There is **exactly one** of each, reused by every surface.

- **Backend:** behaviour lives in the shared service layer (`api::lights`/`media`/`rooms`/`scenes`) and the **provider** — never in a router, never duplicated per caller. Session/`v1`/MCP are three callers of the *same* fn. A provider command (e.g. Sonos source-switch) must succeed **regardless of which device id the surface targets** — coordinator, group, or member. If a UI transform (grouping collapse, companion merge, receiver binding) changes *which id* a command arrives on, the provider/service resolves the right physical target itself; it does not assume the caller picked correctly.
- **Frontend:** every surface (Control / Rooms / Floor Plan / Boards / Media page) renders the **same** shared component (`DeviceControl`, `MediaControls`/`MediaEditor`, `LightEditor`, `GlyphButton`) fed by the **same** API call. A page may *arrange* or *aggregate* these (group tiles, board widgets) but must never fork the control body, the command payload, or the targeting. If two surfaces behave differently for the same device, that is a bug in the shared path, not a reason to special-case one page.
- **When you find a divergence:** fix it in the shared layer so *all* surfaces inherit the fix — adding a per-page workaround is forbidden. A new need gets extracted as a reusable primitive, not pasted into a page.
- **Test the shared contract, not one surface:** a control fix needs a test at the service/provider layer (the level every surface shares), so the next surface can't silently regress.

## Test coverage is mandatory

Every public function, method, and non-trivial private helper must have test coverage. No exceptions.

| What | Where |
|---|---|
| Pure logic (crypto, models, color math, backoff) | `#[cfg(test)]` at the bottom of the same file |
| Provider HTTP behaviour | `#[cfg(test)]` in the provider file, using `wiremock` |
| API layer (routes, auth, DB) | `tests/api.rs` (in-memory SQLite app fixture) |
| Cross-cutting integration | `tests/` as named files |

- **New provider?** Both the `LightProvider`/`MediaProvider` impl AND the `ProviderFactory::build` path need wiremock coverage before it's done.
- **New API route?** At minimum: happy path + unauthenticated → 401.
- **New crypto helper?** Roundtrip + ≥1 failure-mode test (wrong key, tampered data).
- **The full CI gate must pass locally** before any change is complete — all three are blocking:
  ```
  cargo fmt --check
  cargo clippy --all-targets -- -D warnings
  cargo test
  ```
- Don't silence warnings with `#[allow(dead_code)]` to pass — fix the code.
- Prefer real behaviour over mocks (wiremock for external HTTP, real in-memory SQLite for DB). Test public contracts, not internals. One clear assertion purpose per test, named after the behaviour. Large shared fixtures go in `tests/helpers.rs`.

## Backend & process directives

- `ProviderRegistry` is the **single** place provider types are registered — no provider-type match arms anywhere else.
- Credentials are AES-256-GCM encrypted before persisting; never store plaintext.
- The Hue connection manager is the **only** code that reconnects the bridge SSE stream — never open a second stream.
- Session / `v1` / MCP all delegate to the **same shared service functions** (`api::lights`/`media`/`rooms`/`scenes`). Put control/behaviour in the service layer, not per-router; MCP tools are a third caller of those fns, never an HTTP hop back into `/api/v1`.
- Migrations are **append-only**: add the next `migrations/NNNN_*.sql`; never edit a shipped one.
- **In-app event journal (dev mode):** a `tracing` layer (`src/journal.rs`) captures every `bifrost::*` event at debug+ into a ~1000-entry ring buffer **independently of `RUST_LOG`**; `GET /api/dev/events` (+ `/clear`) serves it and Settings → Developer renders it live. This makes the "strong debug logging" convention doubly load-bearing: a `tracing::debug!(target: "bifrost::…")` is both the server log line *and* the in-app debugging surface — device state pushes log under `bifrost::events` at **TRACE, changed-only** (`connection::journal_state_push` — heartbeat echoes are dropped, and a `bifrost=debug` console stays quiet; the journal filter captures that target at TRACE).
- **Reliability is a primary goal** (why Bifrost exists vs HA). Connection managers own reconnection with shared backoff; a live read that can't reach a device falls back to cached state with `reachable: false` rather than failing the whole request.
- **Keep docs in sync as part of the change:** new `/api/v1` route → `docs/api.md`; new assistant capability → `docs/mcp.md`; new provider → the Current providers table.
- **Cutting a release? Use `scripts/release.sh <X.Y.Z> "<summary>"`** (lives in this repo and the kiosk repo). It runs the **CI gate first** (Bifrost: `cargo clean -p bifrost` then `fmt --check`·`clippy -D warnings`·`test`; kiosk: `./gradlew testDebugUnitTest`), then bumps the version **in lockstep with the tag**, commits `Release X.Y.Z — <summary>` (Co-Authored-By trailer), annotated-tags `vX.Y.Z`, and pushes branch + tag. Auto-detects the repo: **Bifrost → `Cargo.toml`+`Cargo.lock`**, **kiosk → `app/build.gradle.kts` (`versionName` + `versionCode`+1)**. Emergency bypass: `SKIP_GATE=1`. It commits *before* the gate (working tree freed; a gate failure leaves the commit local, un-tagged — fix, `git commit --amend`, re-run). **Why the bump matters:** `Cargo.toml`'s version is the single source feeding `env!("CARGO_PKG_VERSION")` → `/api` health → the frontend badge; forget it and the binary + badge silently lag the tag. Run the script instead of doing the steps by hand.

## Frontend & UI conventions

Hard rules for any UI change — the user has repeatedly corrected drift here; treat them as non-negotiable as the test gate. No CSS framework: inline style objects + `frontend/src/styles.ts` (`S`, `ACCENT`) and `theme.ts`.

- **Reusable components, never a forked control path.** Build/adjust controls in the shared primitives and reference them everywhere — never re-implement a control per page/view. Per-device fly-outs route through the one **`DeviceControl`** dispatcher (`components/DeviceControl.tsx`); room/board **aggregate** editors use `LightEditor`/`MediaEditor` **directly** (multi-device, capability-intersected — the intentional exception). Shared blocks: `components/controls.tsx` (`Button`/`Segmented`/`Switch`), **`Select`** (themed dropdown — built-in **search box** for long lists, `option.group` headers, portals **above** modals), **`components/RoomCard.tsx`** (the whole room card — header-as-editor-button, quick controls, one glyph button per member — rendered by Control's `RoomBox` and the Boards Room widget, which supply only the frame; also home of `GlyphButton`, the per-device `LightButton`/`PowerButton`/`MediaButton`, `RoomControlButton`, and the `roomMembers`/`groupedAudio`/`litHexes` derivations), **`GlyphButton`+`nicheStyle`** (the lit device-niche button), `CornerFiligree`, `InlineSlider`, `Modal`/`useDialogs`, **`Flyout`** (`components/Flyout.tsx` — the one anchored-popover/bottom-sheet shell behind every control fly-out; its mobile sheet gets a `useDragToClose` drag-down-to-dismiss handle by **default** on every fly-out, and opt-in `maximize` additionally expands the sheet near-fullscreen for a panel that wants to dominate the screen — e.g. the TV remote's Scrying Glass tab), `components/sheet.ts`, `LightEditor` (wheels/brightness/effects/segments). **Boards** widgets and the **Floor Planner** are *visualizations* that reuse these, never a parallel stack. If something genuinely new is needed, extract it as a reusable component (as `InlineSlider`/`nicheStyle`/the `Select` search were), not a one-off in a page. **Device choosers use the room-grouped pattern** — `components/deviceOptions.tsx` (`deviceSelectOptions`/`groupByRoom`: room headers in name order, "No room" last, names sorted, `Select` search on top) — shared by Boards widget config and the automation editor's subject/gate/target pickers; pre-prefix ids (`light:${id}`) when one Select mixes domains. **`SelectRow`** (`components/SelectRow.tsx`) is the one "selected = lit box" primitive for a list of toggleable items (a coloured border + tinted fill around a checkbox, ≥44px tall) — the Rooms/Media device pickers, the room Presence panel's per-sensor toggles, and `deviceOptions.tsx`'s **`OptionCheckList`** (the multi-select checklist behind Boards group/device-status widgets and the automation editor's target pickers) all render it; its items lay out as a responsive grid (`repeat(auto-fill, minmax(150px, 1fr))`) so a long list needs less scrolling. Never reach for a bare `<input type="checkbox">` for a selectable list item — that's the divergence this primitive exists to prevent.
- **Themed glyphs over emoji — HARD CONSTRAINT.** All iconography is the SVG glyph registry (`components/glyphs.tsx`) rendered via `<Glyph name=…>` (or `GlyphButton`); **never emoji** (off-theme). Missing an icon? Add a line-icon to `BODIES` (`fill:none`, `stroke:currentColor`, `viewBox 24`, the shared `base` props) **and** a row to **`ALL_GLYPH_OPTIONS`** — the single source every glyph picker renders (device override, room control, board button/control), so a new glyph appears in all pickers automatically. Watch the "glyph-name rendered as raw text" bug. **Only carve-out:** the device **Effects** UI may use emoji (its tiles use deliberately literal gradients, not theme accents).
- **One unified design across every device type.** When you change a control's look/behaviour (a fly-out, button, niche, bar), apply it to **every** device type and surface (Dashboard / Rooms / Floor Plan / Boards) in the **same change** — a half-applied restyle reads as unfinished. Power is the shared `GlyphButton`/`PowerToggle` everywhere, lit in the domain accent: **cyan = light, violet = media, gold = power/switch**.
- **Live updates, never remount-to-see.** When one control mutates shared server state another element reflects, the dependent UI must update **live**: lift the shared state to the nearest common parent and have the mutating action call a refresh callback (or consume the `/api/events` **SSE** stream). Never require navigating away and back. Prefer explicit refresh-on-mutation over polling.
- **Desktop uses the width — tile, don't center.** Page containers are full-bleed (`styles.ts` `pageShell(isMobile)`; no `maxWidth`+`margin:auto` shells) and card collections tile with **`tileGrid(minPx, isMobile)`** (`repeat(auto-fill, minmax(...))`, top-aligned) — the **Devices page is the reference**. A centered narrow column is a **compact-only** layout; on desktop a single column is reserved for genuine forms/input stacks, kept at a readable width and **left-aligned** (never re-centered). An expanded/editing card inside a tile grid spans the full row (`gridColumn: "1 / -1"`), and its innards may tile again (the Rooms editor sections do). Prose caps its own line length (PageHeader description); the container never does. Masonry surfaces (`columnCount`) scale their column count with window width (`useMediaQuery`) instead of capping the page.
- **Responsive via `useViewport()`** (`frontend/src/useViewport.ts`) — inline styles can't do media queries. **`isCompact` (≤1024px = phones *and* tablets) is the primary switch:** both get the mobile chrome (top title bar + bottom tab bar in `App.tsx`, touch sheets, stacked/dense cards) because a wall-mounted **tablet is a first-class target** — it must look/feel like mobile, never a shrunk desktop. Anchored fly-outs become bottom sheets via `components/sheet.ts`. `isMobile` (≤640px, phones only) is reserved for what a phone genuinely can't fit (today only the Floor Plan) — not the general switch.
- **Compact-friendly is mandatory for every new UI element**, built in the same change as the desktop path: any picker/popover/menu/dialog/inline editor gets a touch-friendly **bottom sheet** form (full-width, ≥44px targets, scrollable) on `isCompact`; avoid native `<select>`/hover-only affordances in dense rows.
- **≥44px touch targets on compact — enforced two ways** (`theme.ts` exports `TOUCH` = 44): square/primary controls are *actually* ≥44px on `isCompact`; slim chrome that must keep its designed size (switch pills, thin sliders, the close ×, bare-glyph buttons) wears **`hitHalo(w, h)`** — an invisible transparent-padding + negative-margin halo on the outer interactive element, visuals on an inner span. Never ship a sub-44px tap target on compact; never fatten a visual when a halo does the job.
- **Tabbed panels must support swipe.** Any panel whose content is switched by a `Segmented`/tab strip (the TV remote's Keys⇄Scry⇄Apps, LightEditor modes, page-level tab pairs) wires **`useSwipeTabs(value, order, onChange)`** (`components/useSwipeTabs.ts`, generic over any tab count): spread `swipe.handlers` on the gesture surface, **which must set `touchAction: "pan-y"`** (or the browser claims the pan and pointercancels the gesture), and put `swipe.style`/`swipe.className`/`key={swipe.key}` on the sliding content wrapper (drag-follow + slide-in feedback; the tab strip stays outside the wrapper so it holds still) — touch/pen only, no wrap-around; drag-owning surfaces opt out via `data-swipe-ignore` (canvases/inputs/selects are excluded automatically; shared sliders already stop pointerdown propagation; the Scrying Glass gesture slab owns every gesture on it the same way). A new tab set gets the gesture in the same change. (A `Segmented` used as a form *choice field* — e.g. Boards widget config — is not a tab panel and doesn't swipe.)
- **Docs style — greenfield, no archaeology.** In `docs/` (and this file), describe only **current** behaviour + rationale. Don't cite version tags (`(0.27.3)`, "fixed in X"), milestone codes (`M22`), or history ("the old rule was…", "previously", "was rolled back"). Keep the *why*; drop the *when / what-changed*.

## Adding a provider

1. Implement the factory + `LightProvider`/`MediaProvider` (and `discover_groups` if it has native rooms/zones to wrap into Bifrost Rooms).
2. Register it in `ProviderRegistry::default_registry()` (`src/providers/mod.rs`) — the only place provider types are registered.
3. Add a row to the **Current providers** table.
4. wiremock tests for the provider impl **and** the factory `build` path (mandatory).
5. Declare `credentials_schema` so the add-provider form renders the right fields.
